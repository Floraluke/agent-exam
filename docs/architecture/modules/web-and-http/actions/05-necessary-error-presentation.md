## 1. 审计结果：Web 层只有两条通道能见到服务端内容

**通道一（安全）：统一错误码 → 本地固定文案。** `lib/api-client.ts:35` 的 `ApiError` 构造函数用**前端本地**的 `messages[code]` 表取文案，**服务端返回的 `message` 正文从不进入 DOM**；未知或形状不符的错误码收敛为 `UNAVAILABLE`。因此接口层错误天然满足"仅必要呈现"——呈现的是稳定码 + 固定中文，不含任何服务端自由文本。

**通道二（需约束）：服务端自由文本被直接渲染。** 三处：

| 位置 | 渲染的内容 | 风险 |
|---|---|---|
| `features/jobs/batch-report.tsx:18`、`:25` | `stage_message`（批次与每个 Run） | 服务端自由文本 |
| `features/jobs/batch-report.tsx:22`、`:26`、`features/jobs/report.tsx:21` | `failure_code` | 稳定码，风险低 |
| `features/jobs/recovery.tsx:57`、`:59` 与 `features/jobs/report.tsx` | `failure_summary`（恢复页标题写作"安全原因"） | **自由文本，最高风险** |

**写入方的现状**：`failure_summary` 在 `domain/jobs/models.py:115`、`:160` 声明为 `str | None = None`；`application/` 层**没有任何地方写入它**，只有持久化层用 SQL 原样透传（`execution/finalization.py:80`、`recovery/actions.py:47`、`:99`）。

**结论**：今天它实际上恒为 `None`（UI 那个分支基本不会渲染）。风险不在现状，而在**将来**——E 的代理链一旦开始写 summary，就可能把上游主机名、路径、profile 名或令牌片段带进 UI。这正是 B 要在此之前定契约的原因。

## 2. 契约：UI 可呈现什么

| 通道 | UI 可以呈现 | UI 不得呈现 |
|---|---|---|
| 接口错误 | 稳定 `error.code` + 本地固定中文（现表 30 条） | 服务端 `error.message` 正文、`details`、任何堆栈 |
| `failure_code` | 原样显示（受控枚举，如 `BATCH_FAILED`/`BATCH_PARTIAL_FAILURE`） | — |
| `failure_summary` | 受控短文案，**原样呈现**（第 3 节已选 A） | 上游主机/URL、路径、profile 名、令牌或 Key 片段、容器与网络拓扑 |
| `stage_message` | 阶段说明（受控文案） | 同上 |
| 任何位置 | — | 真值与假值哨兵（见第 4 节）在页面文本中零命中 |

**失败关闭**：响应形状不符 → `ApiError("UNAVAILABLE")` → 固定文案，不渲染半成品。

## 3. 已确认的行为决定：A（2026-09-21）

**保持渲染 `failure_summary`，把内容安全约束在写入侧**，不改成码驱动呈现。理由：B 的切片是"仅必要错误呈现"，而"必要"的判据应由**契约与受控文案**共同保证，不该让前端猜测一段自由文本是否安全——猜错一次就是泄漏；同时 §10.2 要求该字段存在，删掉会改动契约语义。

**已落地的契约**：`HTTP_API.md` §10.2 新增一段——`failure_code` 是受控枚举；`failure_summary` 与 `stage_message` 是面向用户的**受控短文案**，不得含上游主机名或 URL、文件系统路径、凭据 profile 名、令牌或 Key 片段、容器与网络拓扑；并明确"内容安全由写入方负责，Web 层不猜测"。

**对 provider 侧（E）的交付要求**：任务 05 的假提供方链与未来任何 provider 实现在写这两个字段时必须遵守上述约束——这是 E 冻结安全合同时应纳入的接口边界，B 不再另立门户。该要求以 §10.2 为唯一权威，本文件只做指针。
