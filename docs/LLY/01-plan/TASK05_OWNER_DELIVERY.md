### 第 7 项要单独说，因为它是唯一会导致返工的

要求原文是"必须定义并验证与供应商相符的输入计数或保守上界；**普通字符串长度不是准确 Token 数**"。两条路：

- **A. 保守上界**（推荐起步）：把字符数按一个偏高的比例折算成 Token，永远高估。实现简单、无需验证 tokenizer；代价是**账本只能承诺"不超过某个上限"，不能承诺精确账单金额**。
- **B. 精确计数**：需要与供应商一致的 tokenizer，并先验证计数结果与供应商实际计费一致。更准，但要额外验证工作量；未验证前同样不能承诺硬上限。

选哪个直接决定账本算法怎么写，也决定后面敢不敢说"硬上限"。**如果不选，E 只能按 A 做，并在文档里写明"不是精确账单"。**

## 3. 第三件：最小替身拓扑实证（建议先做这一件）

### 3.1 要证什么

只有一句话：**做题侧容器除了能到专属代理以外，没有任何其他通路，而受控出网只存在于代理侧。**

权威要求是三组对照，缺一不可：**直连拒绝、宿主隔离、正常模型请求正对照**。

### 3.2 为什么先做

因为这里有一个**未决的技术问题**：项目现有的网络侧车是"Harbor 主容器 + 侧车共享网络命名空间"的结构（其 compose 配置刻意不声明 networks，由执行框架自己附加侧车）。这个结构**不能**承载"只通代理"的边界。所以本片第一个要回答的就是：**这套固定框架是否允许替换或绕过它的网络附加方式。** 这一点只有在你的机器上才能试出来。

如果不可行，任务 05 按停止条件停在这里，不会浪费 E 写完整代理的工时。

### 3.3 用什么做

用**一次性探针**，不是产品代码。探针放在被 Git 忽略的证据目录里（例如 `runtime/prototype/topology-proof-<日期>-<序号>/`），和项目以往所有探针的做法一致（探针脚本 + 配置 + 输出摘要 `summary.json`，保留供复核）。探针**不进入产品源码树**。

做题侧与代理可以先用**最小替身**：一个只做"转发 + 拒绝判定"的脚本就够，不需要实现完整的代理逻辑。

### 3.4 步骤（顺序固定）

1. 起两组网络：内部网络 A 只含"做题侧 + 代理"；代理侧有受控出网。做题侧**不接**出网网络，也不接默认网络。
2. 逐条跑下面的断言，**每条都要留下实际命令与实际输出**。
3. 做一组正常请求的正对照（见下方第 6 条）。
4. 记录网络图、容器/网络/镜像的固定身份。
5. 精确清理：只删除本任务标签下的容器、网络与卷，复核残留为 0；**不执行全局 prune**。
