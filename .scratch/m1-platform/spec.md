# AgentExam M1：Codex 单机评测平台

Status: ready-for-agent

日期：2026-09-11。范围依据为总架构已确认的 M1 交付边界；本规格是其可验收展开，不替代模块、HTTP、数据或认证契约。用户已确认本规格的测试入口与分层验收方式，任务粒度仍需按分任务流程确认。

## Problem Statement

现有 M0 已证明真实 Codex 能完成一项固定任务、产生补丁并交由固定 SWE-Bench-Fork 独立判卷，但它仍是本机脚本原型。协作者无法通过应用提交评测，所有者无法通过平台控制执行授权，也没有持久化队列、可查询的状态、报告和安全证据入口。

项目所有者需要知道每次请求会运行什么、何时才会消耗真实资源、现在进行到哪一步、失败发生在哪个阶段，以及结论由什么证据支持。一个模拟成功页面或一条历史真实运行，均不能证明平台已具备这些能力。

## Solution

交付仅面向受邀团队的 Codex 单机评测平台：协作者登录并从固定任务和已登记配置中提交评测 Job；所有者查看冻结内容后批准或拒绝；本机 Worker 顺序执行已批准的 Job，由 Harbor 管理 Trial，再由固定 Fork 独立判卷。平台持久保存状态和证据，提供进度、结果、安全轨迹、制品及确定性基础排行榜。

先完成可重复的本地软件验证，再验证真实 PostgreSQL/MinIO 接入，最后在单独获得授权后验证真实 Codex 和私有远程协作。M1 不实现 Failure Judge、Quality Judge 或针对 Judge 结论的 Human Review；所有者的运行前批准与安全证据查看仍必须交付。

## User Stories

1. 作为评测机所有者，我希望在本机建立并恢复唯一所有者账号，以便正式执行权有明确归属且不依赖邮件服务。
2. 作为评测机所有者，我希望通过受控邀请让协作者加入并管理成员，以便平台不开放公共注册。
3. 作为协作者，我希望用自己的应用账号登录和退出，以便访问权限与操作记录对应真实应用身份。
4. 作为评测机所有者，我希望网络成员身份不能代替应用登录，也不能由请求正文伪造角色，以便协作者无法取得批准权。
5. 作为协作者，我希望只能查询自己有权访问的非秘密结果，以便任务、报告和制品使用一致的授权规则。
6. 作为协作者，我希望浏览和筛选固定版本的 SWE-Gym 任务，并查看问题描述，以便明确本次评测内容。
7. 作为评测机所有者，我希望任务标准字段与内容哈希固定的原始快照同时登记，以便可以追溯和复现任务来源。
8. 作为评测机所有者，我希望普通页面和被测 Agent 都不能读到参考补丁、隐藏测试或判分答案，以便不泄漏评测专用数据。
9. 作为协作者，我希望从已登记且启用的 Codex 配置中选择，以便不需要提供启动命令或所有者凭据。
10. 作为评测机所有者，我希望通过受控流程登记或禁用固定配置，并保留历史身份，以便配置更新不改变旧报告。
11. 作为协作者，我希望看到 Agent 版本、模型提供方、模型及公开关键配置，以便理解自己选择的完整评测身份。
12. 作为协作者，我希望选择任务、Agent 配置、闭卷赛道和已登记限制模板后看到组合数量，以便在提交前知道评测规模。
13. 作为协作者，我希望非法、未登记、已禁用或超出已登记限制的选择在执行前被拒绝，以便请求不会形成不可执行的评测。
14. 作为协作者，我希望一次提交原子地创建待批准 Job 及全部逐题运行，以便不会出现只有批次而缺少组合的半成品。
15. 作为协作者，我希望重复发送同一幂等请求只产生同一个 Job，不同正文复用同一键得到明确冲突，以便网络重发不导致重复评测。
16. 作为评测机所有者，我希望创建 Job 时冻结任务、Agent、后端版本、赛道、网络/工具策略及限制，以便批准的内容就是随后执行的内容。
17. 作为协作者，我希望提交后立即看到“等待所有者批准”，且请求不等待 Agent 运行，以便明确提交并不等于开始消耗资源。
18. 作为评测机所有者，我希望查看冻结摘要后批准 Job，并留下可信决定者、时间和说明，以便每次执行授权可审计。
19. 作为评测机所有者，我希望批准只使 Job 获得排队资格，不在 HTTP 请求内读取模型凭据或启动 Harbor，以便授权与执行职责分开。
20. 作为评测机所有者，我希望拒绝后 Job 终止、未开始的逐题运行取消且永不被 Worker 领取，以便拒绝具有实际效果。
21. 作为评测机所有者，我希望并发批准、拒绝或重复请求只能形成一个一致的最终决定，以便不产生相互矛盾的审计与执行状态。
22. 作为协作者，我希望能区分等待批准、排队、准备、执行、判卷和收尾阶段，并看到安全的阶段说明，以便知道进度慢在哪里。
23. 作为评测机所有者，我希望 Worker 只领取已批准的队列项，且即使误开两个 Worker 也最多只有一个重型 Job 活跃，以便控制单机资源和避免重复执行。
24. 作为评测机所有者，我希望一个平台 Job 对应一个 Harbor Job、逐题运行对应 Trial，且 Trial 顺序执行，以便保留既有执行映射与并发约束。
25. 作为协作者，我希望每个任务与配置组合只尝试一次，并能查询各自运行身份和结果，以便批量评测矩阵没有重复或遗漏。
26. 作为评测机所有者，我希望只有经过完整性和大小检查的最终文本补丁进入独立判卷，以便不把自然语言自评、截断或错配的文件当作有效输出。
27. 作为协作者，我希望修复是否通过由固定 Fork 在干净环境中的测试结果决定，而不是由 Harbor reward 或模型自述决定，以便结论可信。
28. 作为协作者，我希望“题目未修好”和“基础设施未能完成评测”分别显示，以便不会把缺少可信结果误读为普通失败成绩。
29. 作为协作者，我希望部分运行失败时仍保留已经完成的结果，并明确展示部分错误，以便一场失败不抹掉整个批次的有效证据。
30. 作为协作者，我希望可以取消自己提交的待批准、排队或尚未启动 Trial 的 Job，以便在执行前撤回请求。
31. 作为评测机所有者，我希望可以取消任意 Job，并且执行中取消只阻止后续 Trial，当前 Trial 至多运行到冻结超时，以便按既定策略安全收束。
32. 作为协作者，我希望页面区分“已请求取消”和“已取消”，并保留取消前后的真实证据，以便不会误认为当前 Trial 已被立即杀死。
33. 作为评测机所有者，我希望 Worker、宿主或 Harbor 中断后旧 Job 不自动续跑或重新排队，以便不会出现未经确认的重复模型消耗。
34. 作为评测机所有者，我希望恢复流程能在证据充分时幂等收束，否则明确记基础设施中断，并以新 Job 关联新的重试尝试，以便历史事实不被覆盖。
35. 作为协作者，我希望刷新页面或重启平台后仍能查询已保存的 Job、状态事件和结果，以便进度不依赖某个进程的内存。
36. 作为协作者，我希望从批次矩阵进入逐题报告，再定位对应补丁、测试摘要和安全证据，以便逐项理解判定依据。
37. 作为评测机所有者，我希望制品写入后不可覆盖，读取关联有哈希和大小可核对，以便结果证据可以追溯。
38. 作为协作者，我希望对象存储或数据库失败、正文缺失、上传未完成时得到明确错误，以便不会看到假完整报告或假空文件。
39. 作为协作者，我希望分页查看已脱敏的可观察轨迹事件和必要过程摘要，以便理解执行过程且不接触秘密或私密思维链。
40. 作为评测机所有者，我希望任何通过页面、接口或下载提供的内容都符合输出保护要求，以便本机私有原始输出例外不会被误用为对外发布许可。
41. 作为协作者，我希望补丁超过警告线时有提示，超过硬上限或为二进制时明确拒绝且不截断，以便知道为何没有进入判卷。
42. 作为评测机所有者，我希望原始制品执行单文件和单运行总额限制，所有裁剪都可观察，以便不会无限占用空间或静默损失证据。
43. 作为评测机所有者，我希望只有本机受控维护入口能清理到期大型原始制品，并保留核心结果及删除审计，以便空间管理不损坏历史追溯。
44. 作为协作者，我希望正文已清理时看到明确的已删除状态，仍能查询哈希、大小和时间，而不是被告知记录从未存在，以便理解证据保留情况。
45. 作为协作者，我希望基础排行榜按完整 Agent 配置区分身份、展示确定性结果并单列基础设施错误，以便不会把不同条件或未知结果混成成绩。
46. 作为协作者，我希望过程指标只展示、缺失标为未知，同等确定性成绩保持并列，以便不被虚假的零值或未实现的模型评分误导。
47. 作为评测机所有者，我希望所有测试替身运行严格留在内部测试范围，不进入正式展示、报告或排行榜，以便软件测试不会冒充真实评测成果。
48. 作为协作者，我希望通过获准的私有 HTTPS 入口使用平台，并能按课设约定经 Tailscale 或同一可信物理局域网共用 PostgreSQL 管理员；仍不能直连原始 FastAPI、MinIO、Docker、Worker 或模型端点，以便团队协作保留明确暴露边界。
49. 作为评测机所有者，我希望分别在既有 VPN 开启和关闭时验证获准与未获准设备的访问行为，以便私有协作不破坏现有出站环境或扩大权限。
50. 作为协作者，我希望评测机离线时明确知道入口不可用，恢复在线后历史数据仍存在，以便不把本机离线误认为评测结果丢失。
51. 作为项目所有者，我希望每个开发任务都有可运行的验收和独立行动记录，并在关键节点有本地提交，以便持续掌握已完成、正在做和仍缺的内容。
52. 作为项目所有者，我希望最终 M1 验收同时具备真实平台闭环、安全门槛和双机协作证据，而不是只看模拟演示，以便能判断是否真正达到可用阶段。

## Implementation Decisions

- 保持单机模块化单体：Next.js Web、FastAPI HTTP Delivery 与 Python Worker 是进程角色；不拆微服务、不引入多机调度、Redis 或 Celery。
- 深化已规划的 Task Catalog、Agent Registry、Job Submission、Owner Approval、Job/Run Repository、Job Orchestrator、Execution Backend、Patch Evaluator、Trajectory Recorder、Artifact Store、Reporting 和 Worker Shell 职责；领域层不依赖外部框架，应用层通过小型 Interface 使用 Adapter。
- 使用 PostgreSQL 保存元数据、状态事件及 Job 队列，MinIO 保存不可变制品；不把 Harbor 本地目录直接视为平台数据库，也不把大日志塞入数据库。
- 延续已有 ExecutionBackend 与 PatchEvaluator 这两个真实存在的 Seam；生产 Adapter 与测试替身满足各自 Interface。M0 原型的单题限制及本机证据形式不等于 M1 批量、持久化和生命周期能力已经存在。
- HTTP 请求只校验、调用应用用例并返回状态；执行工作在 Worker 中进行。创建、所有者决定、领取与状态推进使用短事务，不在整个 Agent 运行期间持有数据库锁。
- Job/Run 状态、幂等、授权和快照规则按既有 HTTP 与数据契约实施；每个组合一次尝试。唯一所有者身份来自可信会话，不能由正文或私有网络身份赋权。
- 一个 Job 对应一个 Harbor Job，固定 Trial 并发为 1。为实时阶段、取消和中断补齐生命周期能力时优先深化现有执行 Implementation；若既有 Interface 必须变化，先提出最小契约变更并确认，不通过另造平行执行链绕开问题。
- 最终正确性只来自独立 Patch Evaluator。无可信结果时保留基础设施错误与证据，不伪造确定性失败；后续 Trial 失败不覆盖已完成结果。
- 所有对外内容必须满足现有认证和输出安全契约。仍只在所有者本机私有保存的原始输出例外，不适用于共享存储发布、页面、下载或任何外部分析。
- 保持已确认限额：文本 patch 超过 256 KiB 警告、超过 1 MiB 拒绝且不截断、二进制拒绝；单原始制品 50 MiB、每运行原始制品合计 200 MiB，截断与限额失败均明确记录。
- 核心结果、配置快照、最终补丁及测试摘要长期保留；大型原始制品 30 天后可由所有者本机维护流程清理。M1 不新增定时删除服务，不通过普通 HTTP 提供删除入口。
- M1 报告保留兼容空值：judge_analyses 为空列表、human_review 和 quality_tiebreak 为空、review_status 为 NOT_REQUIRED；不建立分析/复核专用表、路由或空壳依赖。
- 私有 Web 方案沿用 Tailscale Serve 同源入口。共享 PostgreSQL 统一使用 TCP `55432`：当前保留 Tailscale Serve，另按用户决定增加只面向同一可信物理局域网的直连路径；不得做路由器端口转发或公网发布。具体 Compose、防火墙、策略、设备协调和实测进入后续独立授权行动，本规格与本次文档同步不触发这些机器操作。
- 精确技术参数和尚未定义的业务统计规则见 Further Notes；未定案内容不能在实施中默默变成既成事实。

## Testing Decisions

用户已确认：HTTP Interface 是主要验收入口，少量浏览器整流程测试验证页面接线；执行与判卷先采用可控替身，数据库/存储另作真实集成，真实模型与双机验收单独授权。

好的测试观察调用者能看到的行为：响应、权限拒绝、状态变化、冻结身份、证据内容及是否发生外部执行；不依赖私有函数名或内部调用次数。保留真实应用用例、状态规则、请求校验与授权逻辑，只在外部依赖 Seam 注入替身。

| 验证层 | 覆盖范围 | 能证明什么与不能证明什么 |
|---|---|---|
| 本地 HTTP 流程与 OpenAPI 契约 | HTTP Delivery、提交、批准、查询、取消、报告；成功/非法输入/越权/冲突/依赖错误；正文不能提权；受限字段与延期路由不出现 | 证明应用行为和对外契约；执行替身不证明真实模型或容器安全 |
| 小型浏览器整流程 | 登录、选择、提交、所有者决定、状态刷新、报告/证据链接、权限与错误显示 | 证明页面与后端接通；不替代数据库并发或安全实测 |
| PostgreSQL/MinIO 集成 | 事务回滚、幂等、并发决定、双 Worker 领取、全局单活跃 Job、租约校验、不可变对象、断流与两侧故障、读取/删除审计 | 证明真实 Adapter 和持久化；不能仅以内存或本地文件替身代替 |
| 已有执行/判卷契约回归 | 身份/哈希/大小校验、空补丁、无效输出、缺少可信结果、证据不覆盖、内部测试隔离 | 沿用已有 M0 契约与独立判卷测试先例；实际运行时记录通过、失败和跳过 |
| 最终受控验收 | 新平台入口上的真实 Codex→补丁→固定 Fork→持久化报告、相关安全门槛、私有远程双机正反例 | 必须在独立授权后取得新证据；旧 M0 记录仅作基线，不能替代 M1 验收 |

必测不变量：

- 创建和批准 HTTP 请求均不启动 Agent；待批准/已拒绝 Job 不可领取。
- 单机同时最多一个重型 Job；错误 Worker 身份、租约或版本不能推进状态。
- 执行中取消停止后续 Trial，不强杀当前 Trial；中断不自动续跑/重试。
- 题目未解决、未知结果、基础设施失败及部分完成分别可观察。
- 内部测试不能进入正式报告和排行；指标未知不写 0，确定性并列不被模型评分打破。
- patch 与原始制品阈值均测临界值及越界；正文缺失、截断、已删除和未就绪不伪装成正常完整内容。
- 页面、响应、下载、日志及可共享存储不泄漏凭据、私有路径、隐藏答案或不应公开的原始内容。

测试状态：本规格行动只做文档验证，以上 M1 业务检查尚未执行。M0 已记录的历史测试与真实结果不计作这些检查的新通过记录。

## Out of Scope

- Failure Judge、Quality Judge、Judge 结论 Human Review，以及它们的专用表、路由、工作台和后台调用。
- Aider/Claude Code 正式接入、自研 Agent 提交审核、P2 受控模型提供方实现；保留既有扩展位置即可。
- 开卷实验赛道、任意 shell/源码运行、自定义模型地址/代理或用户任意资源配置。
- 多机执行、Kubernetes、云端常驻控制面、微服务拆分及提高重型并发。
- 公共注册、邮件服务、公开互联网发布，以及以 Tailscale 身份替代应用登录。
- 自动重试、崩溃自动重新排队、立即强杀取消、过程指标计分和主观质量加分。
- 定时制品删除服务、公开制品删除接口或对旧证据的覆盖式修订。
- 为本轮规格自动执行模型、Docker/网络探针、真实凭据实验、设备配置、外部任务发布或 Git 推送。

## Further Notes

1. M1 是否完成以全部适用验收证据为准，而不是以规格、任务单或某个模块提交为准。M0 剩余安全/生命周期验收不因开始 M1 被自动豁免，具体缺口仍由 Harbor 与认证专题维护。
2. 身份业务已确定，但账户、密码哈希、邀请、会话和本机恢复的实际存储与 HTTP 端点尚未实现。身份任务开工前须说明已有职责能否承载；需要新 Module、Interface、表或目录时先取得用户确认。
3. 任务规模预设、最多约三个配置、租约/心跳时长、数据库类型/索引和库版本中的候选值，要在对应任务中查证并锁定。规格不把“约”偷偷转换成精确限制，也不替代依赖核验。
4. 基础排行榜的重复 Job/手动重试结果选择、统计分母和可比范围尚需明确的最终口径；按完整配置分组、内部测试排除、基础设施错误单列和确定性并列保持不变。排行任务实施前提出最小口径选择，由用户裁决，不猜测业务规则。
5. 已有执行 Interface 当前同步返回整批 Trial 结果。实时进度、取消停止后续 Trial 与中断幂等收束需要在相关任务中核对固定 Harbor 能力，必要时确认最小 Interface 变更；不能改成一个平台 Job 对应多个 Harbor Job。
6. Spec 与后续任务只描述交付和验收；每次实施仍有独立行动记录，并按用户授权在关键节点建立范围清晰的本地提交。任务依赖和粒度在正式发布任务单前确认。
