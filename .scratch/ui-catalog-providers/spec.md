# 角色化 UI、扩充题库与 Codex 多提供方规格

> 2026-09-17：业务选择与长期持久化前移已确认，具体任务拆分及技术候选待审阅；只处于计划阶段。`needs-info` 不撤销已确认选择。

## Problem Statement

当前 owner（所有者）与协作者使用同一长页面，提交、审批和报告不够容易理解；仅有一道可选题，无法充分比较配置。用户希望先反复看 HTML 原型，再分阶段改 UI、增加至少五道题、接入 DeepSeek 与 Kimi 的按量 API；过程可以随时暂停，不要求近期完成。

## Solution

采用电脑主工作台、手机完整可用的浅色界面。首页按角色区分；共享评测详情与报告，用三步向导提交，用同题跨配置矩阵读结果。扩充现有固定题库，而非新造数据来源；沿原 Job/Run、批准、Worker、Harbor、固定 Fork 链接入两家 API，真实 Key 留在隔离代理。原 ChatGPT 配置继续可用。

业务规则正文以本规格为准；技术边界分别由架构、数据模型、模块及接口文档维护。历史问答见[规划行动](../../docs/actions/2026-09-17-ui-catalog-provider-planning.md)，执行拆分见[计划](plan.md)。

## User Stories

1. 作为 owner，我希望首页优先看到待批准、执行中与异常评测，以便知道下一步该做什么。
2. 作为协作者，我希望首页突出新建评测、我的评测及结果，以便不用理解后台管理功能。
3. 作为任一角色，我希望电脑和手机都能完成本角色全部操作，而不只是查看精简页。
4. 作为用户，我希望先看可点击的浅色 HTML 原型、比较布局并逐轮修改，再开始产品代码实现。
5. 作为用户，我希望导航把工作台、评测、题库、配置及 owner 管理分开，且当前所在位置明确。
6. 作为提交者，我希望按“选题→选配置→核对提交”完成新建，前后切换不丢选择。
7. 作为提交者，我希望每批任选 1–20 道不同题、最多三个不同配置，并看清题数×配置数和最多 60 次 Run。
8. 作为提交者，我希望看到准确的运行限制及“提交后等待 owner 批准”，而不是误以为按提交已启动模型。
9. 作为提交者，我希望提交中的重复点击被阻止、可安全重试不确定请求，且已成功创建的 Job 不被重复创建。
10. 作为 owner，我希望仍可提交并批准自己的 Job；双角色验收需要不同人不应成为产品禁令。
11. 作为 owner，我希望审批页看到冻结题目、配置、规模与限制，能批准、拒绝、取消，并看清操作结果。
12. 作为原提交者，我希望重试创建新 Job/Run、关联旧 Job、保留原访问权，并再次等待批准；恢复不会自动续跑。
13. 作为用户，我希望断网、登录过期、无权限、空列表、排队、运行中、取消和基础设施故障都有明确提示。
14. 作为用户，我希望有筛选与分页可查旧 Job，刷新/链接能返回指定 Job；不把某页 UUID 顺序当最近时间。
15. 作为用户，我希望状态依据服务器数据展示，缺少 Worker 在线证据时不显示虚假的“Worker 健康”。
16. 作为用户，我希望新增至少五道已完成离线资格验证的题，优先复用现有 mypy 项目。
17. 作为用户，我希望保留现有题与历史记录，新题镜像、数据身份和判卷能力有证据，而不是只有选项。
18. 作为用户，我希望参考补丁能通过、空/错误补丁不能通过；题目答案与隐藏测试不出现在做题侧和网页。
19. 作为用户，我希望能选择现有 ChatGPT、Codex + DeepSeek-V4.1-Flash、Codex + Kimi K3 配置。
20. 作为 owner，我希望用 Kimi 开放平台按量 API，而非 Kimi Code 订阅；不因接口差异被静默换模型。
21. 作为 owner，我希望仅在评测机私有文件中管理真实 Key，网页只显示提供方、型号和非秘密标识。
22. 作为 owner，我希望做题容器只能拿到受限、短命的 Run 令牌，无法读取或转发长期 Key。
23. 作为 owner，我希望有明确验收预算、限额和停机条件；估算不是账单保证，也不意味着已授权花费。
24. 作为用户，我希望报告先展示各配置通过题数、耗时和可获得用量，再看“每题一行、配置一列”的结果。
25. 作为用户，我希望分清未通过、执行故障和未完成；未知费用/用量显示未知，缺失轨迹不伪造补齐。
26. 作为用户，我希望从对比单元格进入单次结果和安全制品；访问权限、过期制品提示和原始秘密保护不减弱。
27. 作为用户，我希望看到影响可比性的限制差异，既有排行榜规则不因换 UI 被偷偷改动。
28. 作为 owner，我希望计划与权威文档同步，任何阶段暂停后都能按证据恢复；长期持久化、备份恢复及端口隔离在 HTML 原型后、正式组内使用和真实模型 API 前完成。

## Implementation Decisions

### 已确认的范围

- 两角色首页、三步向导、浅色工作台、桌面优先/手机完整、报告优先跨配置比较。
- UI 结构采用任务 01 的纯 A「侧栏工作台」；B「紧凑任务收件箱」和 C「分区概览」仅保留为历史比较，不混入产品基线。
- 正式 UI 的每个按钮、链接、表单提交、筛选、分页和可操作状态都必须追溯到前端处理及现有 HTTP/后端契约；纯前端动作显式标注“无后端请求”。不存在的接口先标缺口并请用户确认，不为迁就界面臆造 API。
- 新提交规模变为连续 1–20 道、1–3 配置；新版本策略承载，历史冻结值、摘要、可比性与权限不追溯改写。
- 新题优先固定 SWE-Gym Lite 中的 mypy 候选；以资格门禁决定可登记集合，不开放任意文件/镜像/数据 URL。
- 保持 Codex CLI 固定版本，DeepSeek API 名 `deepseek-flash`、Kimi `kimi-k3`；两者原生 Responses，不做协议转换，不使用订阅端点。
- 已批准 B 的隔离代理方向与必要内部子目录/私有网络。它是已有执行适配器的内部实现，不是新业务 Module、第二个 Worker、队列或判卷器。
- Key 仅由 owner 本机私有文件管理；创建 Job、审批和 Web 进程均不读取 Key。Run 执行预检通过后才由可信侧绑定，生命周期按认证合同。
- 所有新增配置只从服务端受控预设登记；协作者不能写模型地址、网络策略、命令、Key 或限制。闭卷与原有审批门禁保留。
- 原有 owner 自提交自批准合法；任务 14 的双角色演示限制不是产品约束。

### 尚待技术收敛，不可当成已实现

- 精确内部文件树、代理容器拓扑与私有文件格式/权限、请求字段白名单、账额预留/中断处理，见实现地图与认证合同；05 开工先验证安全可行性再接真实 Key。
- 两家官方模型目录、推理参数、提示模板/工具描述和返回用量必须在固定 CLI 下核验并冻结；官方 alias 可能漂移，记录请求与实际返回身份，不声称不可变权重。
- 只扩展既有快照和目录约束，不计划新增数据库表；若技术核对证明必须增加表或业务 Interface，停止该分支，说明原因后请用户决定。
- 新 API 限额不能自动覆盖旧 ChatGPT Job；对比页显示不同限制，不据不同实验条件生成新的“公平排名”。当前 `cost_usd` 只能承载可信美元费用；人民币估算不填进去。

## Testing Decisions

主入口继续用 HTTP 测试业务行为，少量浏览器验证操作链与手机布局，隔离真实 PostgreSQL/MinIO 验证事务、冻结数据和存储。UI 不依赖真实模型；题目资格用固定 Fork 离线判卷；代理先用假 Key/假提供方，再在明确授权下做单题真实工具循环，最后执行冻结矩阵。完整验收规则由[验证计划](verification.md)维护。

测试复用现有身份、目录、提交/审批、批次报告、取消/恢复、排行榜、证据与保留清理接口。既有配置探针只证明固定 CLI 加载配置并向假入口发出正确请求，不证明真实模型或代理隔离已通过。

## Out of Scope

本次规划不实施产品代码，不生成 HTML，不新增真实调用，不充值；不升级固定 CLI/Harbor/Fork、不改第三方仓库、不加入 Chat/Responses 桥接、自研 Agent、LLM Judge、Web Key 管理、健康监控服务、计费平台、自动充值或公网发布。长期部署已作为独立 P 阶段前移，其范围在[持久化规格](../persistence-deferred/spec.md)维护，当前仍不执行。已有任务 14 未完成项保持独立，不在本规格中宣布完成。

- 原八项及独立 P 阶段的具体任务粒度仍属计划草案；前移依赖已经确认，未正式发布 ready-for-agent 任务单。
- 长期暂停后先复核 Git、源码、模型/价格/接口和缓存身份；遇到变更记录差异，不重复运行旧探针来刷通过数。
- 持久化另见[已前移的 P 阶段](../persistence-deferred/spec.md)。
